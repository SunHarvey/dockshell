## 1. 已确认的范围与操作

- 每个顶层标签容纳一个或两个面板，支持左右分屏及上下分屏。
- 只有一个面板时，选择分屏方向会打开已保存会话选择器。用户可选择与原面板相同或不同的会话配置，确认后新建独立 SSH 连接。
- 已有两个面板时，方向操作只调整布局，不创建第三条连接，不重新认证已有连接。
- 每个面板拥有自己的终端、连接状态、认证提示、错误提示和手动重连。
- 点击面板切换当前输入目标；输入只交给对应连接。后台面板仍接收输出并回复它自己的终端协议查询。
- 拖动原生分隔线调整比例，按每个终端的实际字符网格分别同步远端 PTY 尺寸。
- 调整方向、拖动分隔线或切换顶层标签时，保留已有终端视图、历史、终端模式和连接。
- 面板上的关闭动作只关闭该面板。两个面板中任意一个关闭后，另一个扩大为单面板并继续运行；顶层标签身份保持稳定。
- 标签条上的关闭动作结束该标签内全部面板；最后一个面板关闭后移除该标签。

本轮不增加嵌套分屏、三个或更多面板、拖动排序、多窗口、布局持久化、批量发送、SFTP、端口转发或其他第二阶段功能。现有离线终端与会话管理继续沿用，分屏只作用于远程 SSH 工作区。

## 2. 结构与所有权

| 类型 / 层 | 本轮职责 |
|---|---|
| `TerminalTabSession`，Features | 保留 M7 的单连接运行身份，拥有独立 controller 与 prompts |
| `TerminalWorkspaceTab`，Features | 顶层标签的稳定身份，持有一至两个单连接运行实例、当前面板 ID 和方向 |
| `TerminalTabsViewModel`，Features | 管理顶层标签、创建分屏、当前面板、方向切换、面板关闭和标签关闭 |
| `TerminalWorkspaceLayout`，Features | 用布局值快照向原生宿主表达标签 ID、面板 ID、当前面板 ID 与方向 |
| 会话选择器，Features | 展示已保存会话，选择新面板目标；只显示非敏感配置，不复制或显示凭据 |
| 每标签的 `NSSplitView`，Features / AppKit | 持久容纳对应的原生终端宿主，负责实际分隔线、比例和子视图尺寸 |
| `SSHSessionPane`，Features | 每面板自己的状态、重连、关闭与认证提示 |
| `SSHSessionController` / `TerminalViewController`，TerminalUI | 延续每连接 IO 与生命周期，提供当前呈现的焦点许可 |
| `TerminalViewBridge`，TerminalUI | 继续隔离 SwiftTerm；限制自动抢焦点，向上报告实际获得焦点的面板 |

`TerminalSessionFactory` 仍创建单连接运行实例，分屏不会把一个 controller、prompt continuation、PTY 或 IO 通道同时交给两个面板。应用仍共享既有 Keychain、known_hosts 和设置服务 Actor；UI 与业务模块不直接选择 SSH 后端。

顶层标签 ID 与面板运行 ID 分开。标签初始化时可采用首个运行实例 ID，但关闭首个面板后不能用幸存面板的 ID 替换顶层标签 ID。这样标签选择、原生 splitter 缓存和其他标签引用都保持稳定。

## 3. 保留视图、比例与尺寸同步

每个顶层标签持久持有一个原生 splitter；每个面板持久持有原来的 `NSHostingView<SSHSessionPane>`，其中的终端 representable 只创建一次。新面板只添加它自己的 arranged subview，关闭只移除所属 view。方向切换、分隔线拖动和窗口缩放调整现有 frame，不重新设置已有 root view，不从原父容器拆走仍运行的终端。

当前 M7 的 `detach` 会异步断开连接，IO pump 在没有 surface 时仍可能消费输出。因此本轮不能依赖“先拆卸、再重挂、之后恢复连接”的布局方式；要实际验证 `ObjectIdentifier`、连接计数和已有终端内容保持不变。

SwiftUI representable 必须收到布局与面板的值快照，不能只传入稳定的模型引用。M7 已实际遇到引用参数不变而跳过 `updateNSView` 的问题，本轮延续该修复。

分隔线比例按标签持有；方向切换和窗口尺寸变化后按可用空间恢复。程序调整布局时，应避免 native delegate 把尚未完成的新几何位置反写成用户选择的比例；普通连接状态或尺寸状态刷新也不能把用户刚拖动的分隔线重新居中。

早期检查提出过无条件 `layout()` 和 native resize delegate 可能覆盖拖动 frame 的风险，但那是源码推演，未被确认为真实交互故障的根因。当前源码已增加结构重排标记和已排列尺寸，只在面板集合、轴或 bounds 变化时恢复比例；普通状态 / layout 保留 native frame。程序布局期间也抑制中间几何位置反写比例。

最新独立原生验证改用实际 `NSSplitView` 的 `mouseDown` tracking、完整拖动 / 松开事件和 AppKit 事件循环，已观察第一面板宽度变化，之后继续完成跨方向比例、窗口缩放、每面板 PTY 尺寸和释放检查。窗口缩放以当前 frame 的增减量为目标，避免固定目标超出屏幕可用高度后被系统夹取。测试不是再次调用 `setPosition` 代替 tracking。CUA 拖动本应用分隔线和系统 `NavigationSplitView` 侧栏分隔线都没有产生移动，现只记为该自动化路径受限；真人拖动仍待单独复验。

最小面板尺寸需要按当前可用宽高夹取。在最窄窗口且侧栏较宽时，不能同时满足两个固定的 240 点宽度；native delegate 的最小 / 最大位置必须仍有合法区间。面板头部和提示应允许截断或换行，不能让关闭、断开和重连按钮被固定最小宽度挤出可见范围。

实际原生夹具另发现：140 点高的上下分屏中，旧 `ZStack` 认证提示会把面板头部挤到负坐标，连接 / 取消按钮也超出面板。现改为终端上的 `overlay`，主机确认与密码表单各自放入 `ScrollView`，不再提高终端的最小高度。永久回归使用独立密码 continuation，确认终端与滚动视口都在面板内，并通过原生 scroll document 滚到完整操作行；取消提示后继续验证连接关闭及视图释放。此项验证表单几何和操作可达性，不代替真实密码、field editor 或 IME 交互。

每个终端仍由它自己的 `TerminalSurface.terminalSize` 产生字符列数和行数，再通过所属 channel 的 resize 同步 PTY。不能把整个工作区像素宽度或另一个面板的网格直接发送给服务器；也不能把两个面板列数必须相同当作尺寸正确的依据。

## 4. 焦点、协议回复与认证隔离

M7 只需要防止隐藏标签抢焦点。分屏中两个面板都可见，原来的 `isHiddenOrHasHiddenAncestor` 检查已不足够：认证完成时 controller 会调用 `surface.focus()`，非当前面板也可能因此抢走键盘焦点。

本轮将“允许自动获取焦点”与“接收终端协议”分开。只有当前标签的当前面板允许自动恢复终端焦点；用户主动点击另一个可见面板时，应允许标准 AppKit responder 转移，并更新当前面板身份。不能为了阻止自动抢焦点而拒绝所有非当前面板成为 first responder。

自有 `focus()` 和原生 `mouseDown` 入口会记录标准 responder 转移的结果；需要延后的回调在 MainActor 上确认窗口当前 first responder 仍是该终端。原版 SwiftTerm 的 `becomeFirstResponder` 不是可由外部模块重写的 open API，本轮没有重写该方法或修改第三方源码。关闭、切换或新面板挂载后过期的回调不能把选择又改回旧面板；状态刷新不能把焦点从正在输入的 SecureField 拉回终端。

AppKit 的共享 field editor 可能位于面板子树之外。宿主除检查 first responder 的 view 归属外，还检查 field editor 的 delegate 是否属于目标面板，避免点击认证表单后又把焦点从所属输入控件清走。提示和输入法的实际操作仍须通过对应测试，而不是仅凭这个归属检查宣布完成。

SwiftTerm 的 delegate `send` 同时承载用户输入与 DSR 等终端协议回复。隐藏或非当前面板也需要回复服务器的光标查询，因此本轮不能简单地在所有 `send` 或 `receiveInput` 入口加入“不是当前面板就丢弃”的过滤。应通过 first responder 和命中测试路由真实用户操作，协议回复继续交给产生它的面板连接。

每个面板的主机确认、密码与私钥口令都使用它自己的 prompts 与 request UUID。面板关闭必须取消自己的待答 continuation、IO 和连接回收链，不能调用其他面板的 `cancelAll()`，不能把关闭主面板误当成关闭整个标签。所有秘密仍只在内存及 Keychain 中流转，不写入数据库、布局记录或诊断日志。

真实中文 IME 的候选位置、组合中点击另一面板、取消组合以及最终提交归属需要单独人工验收。合成 `NSTextInputClient` 输入只验证桥接契约，不冒充真实输入法测试。

## 5. 构建和复现入口

现有开发入口继续使用 Command Line Tools，不要求安装完整 Xcode 或登录 Apple 账号。先退出旧 DockShell，再从工程目录运行：

```sh
cd "/Users/harvey/Documents/github-code/DeckShell"
sh Scripts/run.sh zh-Hans
```

完整默认回归和资源搬迁：

```sh
sh Scripts/test.sh
```

包括原生终端和工作区的界面验证：

```sh
DOCKSHELL_UI_SMOKE=1 sh Scripts/test.sh
```

Release 对应入口：

```sh
DOCKSHELL_UI_SMOKE=1 sh Scripts/test.sh release
```

已构建后，M8 独立模型和原生宿主入口为：

```sh
export DOCKSHELL_ROOT="$PWD"
. Scripts/common.sh
bin_path=$(swift_build -c debug --show-bin-path)
DOCKSHELL_SPLIT_TEST=1 "$bin_path/dockshell-verify" "$PWD/Build/debug/DockShell.app" --ui-smoke
```

`DOCKSHELL_SPLIT_TEST=1` 选择 M8 模型验证，`--ui-smoke` 额外创建实际原生分屏宿主。夹具使用合成通道和临时仓库，不连接真实服务器、不访问正式 Keychain 或个人私钥。它不能与性能、真实网络渲染、Keychain 重启或 M7 独立模式同时启用。

最终完整回归日志为 `/private/tmp/dockshell-m8-debug-final.log` 与 `/private/tmp/dockshell-m8-release-final.log`，两轮退出码均为 0。每份各包含三条 `PASS verification completed`，分别对应默认、UI 和搬迁验证；各有全部四条 M8 UI PASS，并以 `PASS relocated app: explicit bundle resources and local signature` 结束。

此前独立 Debug 的 `/private/tmp/dockshell-m8-native-and-compact-auth-test.log` 已覆盖最小高度认证滚动回归，`/private/tmp/dockshell-m8-runloop-resize-delta-test.log` 已覆盖原生 tracking 与缩放；更早的 `/private/tmp/dockshell-m8-split-debug.log` 仅保留历史调试价值，不代替新事件循环入口的结果。本地预览产物仍以实际生成和启动记录为准。

验证入口现增加严格的最终标记：`dockshell-verify` 只有在本轮选中的全部检查成功返回后，才打印完整一行 `PASS verification completed`；`Scripts/test.sh` 对默认、UI 与搬迁三次调用都同时检查退出 0 和该标记。只有 `--ui-smoke` 分支会在 async main 首次挂起前同步进入 `NSApp.run`，让原生 tracking 的嵌套事件循环和后续异步检查都能正常返回。旧 async main 入口可能在 tracking 后提前结束，因此退出 0、部分 PASS 或进入 tracking 的诊断均不算完成。默认无 UI 路径与 M6 内部 Keychain 子进程的固定单行协议保持原有行为，子进程结果由父验证器检查。

若工具环境限制 SwiftPM 构建子进程，继续使用既有的 `DOCKSHELL_DISABLE_SPM_SANDBOX=1`；正常终端不必设置该变量。它不改变外层工具权限、系统安全策略或第三方源码。

## 7. 继续保留的限制

- macOS 14 实机 / 虚拟机尚不可用；当前部署目标和静态标记不能替代目标系统运行。
- 真人鼠标拖动分隔线仍需复验；原生 tracking 自动检查已通过，CUA 拖动同时受限于本应用与系统侧栏，不能据此认定产品拖动失败。
- 真实睡眠唤醒与网络切换后的组合验证仍需要对应操作环境；不主动让用户主机睡眠。
- 最终包真实中文 IME，以及本轮分屏间切换时的候选、组合和提交归属仍需人工验证。
- 真实 VM 密码保存到 Keychain、完全退出应用后重启回读登录，仍按独立验收项记录；历史临时密码登录或合成密码回读不替代它。
- 当前没有 Developer ID 证书，未进行正式签名、公证或官网发布。本轮产物为 ad-hoc 本地预览，未标记为可公开分发。
- M7 曾观察同窗口两个终端列数不同，但各自与远端 PTY 一致。其初始字体与显示缩放尚未取证，本轮不通过连接期间重设字体或修改上游来掩盖；详见 [M7 说明](../M7/多标签开发方案.md)。

M6 的单终端吞吐和 M7 的双连接短时空闲数字分别属于原阶段测量，不能复制为 M8 分屏性能结论。M8 只引用上一节自己的短时采样；整体内存随存活终端及其有限历史增加。
