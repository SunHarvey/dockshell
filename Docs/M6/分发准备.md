# M6：官网分发准备

本轮按已确认的范围制作 **Apple Silicon（arm64）本地预览包**。开发、编译、运行和预览签名继续只使用当前 Command Line Tools，不需要安装 Xcode，也没有登录 Apple 账号。正式 Developer ID 签名、公证和网站发布属于后续明确授权的操作；本轮没有执行。

## 1. 产物与边界

预览产物包含 `DockShell.app`、保留资源与嵌套签名的 ZIP、`ReleaseManifest.plist` 和 ZIP 的 `SHA256SUMS`。产物放在 `Build/distribution/` 下带版本、架构、模式和 UTC 时间的独立目录；不会覆盖 `Build/debug/` 或 `Build/release/` 的开发应用。

预览采用 ad-hoc 签名并启用 Hardened Runtime，便于在本机检查正式运行约束。它没有 Apple 身份链和公证票据，不能视作可公开分发版本。清单中的 `notarized`、`publiclyDistributable` 均为 `false`。工具不会移除 quarantine、关闭 Gatekeeper，或把预览包声明为已公证。

本轮选择 arm64，构建较快、包体较小。脚本预留 `--universal`：分别构建 arm64 / x86_64，核对两份资源一致后用 `lipo` 合并。**本轮没有执行双架构构建，也没有 Intel / Rosetta 验收。**

## 2. 本地预览与复查

在项目根目录执行：

```sh
sh Scripts/release.sh --local-preview
```

如果运行环境限制 SwiftPM 的构建子进程，沿用现有构建方式：

```sh
DOCKSHELL_DISABLE_SPM_SANDBOX=1 sh Scripts/release.sh --local-preview
```

这只调整本次 SwiftPM 构建子进程，不修改系统安全设置。正常环境不必设置该变量。

脚本固定使用根目录 `Package.resolved`，不会自行升级依赖；发行编译使用 `.build/distribution-arm64/`，本地化工具使用 `.build/distribution-tools/`。初次构建需要访问上游包，或已有固定提交的 SwiftPM 缓存。当前受限环境复用了本仓库已经获取的原版镜像，没有修改第三方代码。CLT 的 native 构建器和 `--skip-update` 在当前 Swift 中有弃用提示，现阶段保留它们以继续处理原版 SwiftTerm 的 Metal 资源；未来工具链升级需复核。

将下列路径替换为脚本输出的完整产物路径：

```sh
sh Scripts/audit-release.sh "Build/distribution/产物目录/DockShell.app" --mode local-preview --architectures arm64
sh Scripts/test-release-scripts.sh "Build/distribution/产物目录/DockShell.app"
```

在产物目录校验 ZIP，再解压到其他位置运行，确认应用不依赖构建目录：

```sh
cd "Build/distribution/产物目录"
shasum -a 256 -c SHA256SUMS
ditto -x -k "DockShell-0.1.0-1-arm64-local-preview.zip" "/tmp/DockShell-preview-check"
open "/tmp/DockShell-preview-check/DockShell.app"
```

`open` 仅用于本机预览；由网站下载时的 Gatekeeper 行为需要正式 Developer ID 和公证链单独验证。不要通过改变系统策略来替代该验收。

## 3. 签名与离线审计

应用及 `Contents/Helpers/dockshell-ssh-helper` 都启用 Hardened Runtime。签名顺序为 helper 在先、外层应用在后；签名操作不使用 `--deep`，仅递归验证时使用它。Apple 的嵌套代码规则要求从内到外建立封印。[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)

`Packaging/Release.entitlements` 是空字典。当前原生代码不需要 App Sandbox、JIT、未签名可执行内存、关闭 library validation 或 `get-task-allow` 例外。预览显式关闭时间戳联网请求；正式签名要求 secure timestamp。Developer ID、公证所需的 hardened runtime 与签名要求以 Apple 文档为准。[Apple 公证前提](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

`audit-release.sh` 检查：

- 主程序、helper、两种语言、SwiftTerm shader 和许可证随包存在，且此布局无符号链接。
- app 与 helper 架构完全一致；Mach-O 每个架构的最低系统为 macOS 14.0。
- 两份可执行代码均具有有效签名、Hardened Runtime 和空 entitlements。
- 动态库依赖仅来自系统路径或 Swift 系统运行库，没有 Homebrew / 构建机的动态库。
- Developer ID 模式额外验证 Apple Developer ID 身份链、secure timestamp，以及 app / helper 相同 TeamIdentifier。
- `--require-notarized` 才验证 stapled ticket 和 Gatekeeper；该选项不能用于本地预览。

资源存在性与 Mach-O 检查属于静态验证。ZIP 解压后运行、读取本地化及 shader、真实 SSH helper 通信，仍由验收工具和人工操作验证；不会以静态检查替代实际目标系统测试。Release 去除调试符号不等于证明二进制中绝无任何编译路径字符串。

系统 Keychain 与 helper 的调用方验证都依赖代码身份。正式发布后应持续使用同一 Developer ID 团队、bundle identifier 和 helper identifier；不要通过放宽 Keychain ACL 或跳过对端签名校验解决身份变化。签名需求的 Apple 身份链由官方 requirement 语法校验。[Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

## 4. 正式签名准备（本轮未执行）

本机当前可用签名身份数量为 **0**。只有显式提供已存在且有效的 `Developer ID Application` 身份时，以下入口才会构建正式签名包；找不到身份立即停止，不会降级成 ad-hoc。

```sh
security find-identity -v -p codesigning
sh Scripts/release.sh --identity "Developer ID Application: 你的证书名称 (团队标识)"
```

脚本也接受该有效身份的完整 SHA-1 标识。它只读取公开身份列表，不导出私钥。正式签名调用 `codesign --timestamp --options runtime`，可能访问 Apple 时间戳服务；签名完成后仍未上传、未公证、未发布。

将来决定发布通用包时可额外传入 `--universal`，并先补齐真实 Intel / Rosetta 与 macOS 14 验证。当前 arm64 结果不能代表这些环境。

不安装 Xcode 不妨碍当前工程的开发和本地预览。正式 Developer ID / 公证要求 Apple 开发者身份与服务认证，不能由 Homebrew 或 ad-hoc 签名替代。本轮不会要求账号登录，也没有创建或导入证书、公证凭据。

## 5. 公证准备（本轮未上传）

2026-10-28 本机检查结果：当前 CLT 提供 `notarytool 1.1.3 (42)` 和 `stapler`，路径位于 `/Library/Developer/CommandLineTools/usr/bin/`。其他机器须自行检查；脚本找不到工具会明确停止，不假定每个 CLT 版本都具备它们。

```sh
xcrun --find notarytool
xcrun notarytool --version
xcrun --find stapler
```

公证脚本只接受 **已经存在于 Keychain 的 notarytool profile 名称**。不接受 Apple ID、密码、API 私钥路径等参数；不从环境变量、数据库或仓库文件读取凭据，也不自动创建 profile。未来明确授权上传后，才执行：

```sh
sh Scripts/notarize.sh --submit "/完整路径/正式签名的DockShell.app" --profile "已有配置名称"
```

它首先验证 Developer ID、时间戳、helper 和资源签名；通过后复制应用到独立审核目录，上传 ZIP，保存 submission UUID 和 JSON 结果，再等待最多 10 分钟。等待超时不代表服务端已取消，使用同一 UUID 继续，避免重复提交：

```sh
sh Scripts/notarize.sh --resume "提交的UUID" --app "/完整路径/同一正式签名的DockShell.app" --profile "已有配置名称"
```

Apple 返回不接受状态时保存可取得的 JSON 日志，不生成发行 ZIP。成功后仅对审核副本 staple，再验证 ticket、Developer ID 和 Gatekeeper，最后重新生成 ZIP 和 SHA-256。Apple 要求上传的归档保留应用结构；staple 改变应用容器，因此交付归档必须在 staple 后生成。[Apple 自定义公证流程](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)

脚本不会发布网站，也不会自动宣布目标系统验收通过。macOS 14、IME、睡眠唤醒、真实网络和长时资源占用的测试结果见本阶段独立验收记录。没有这些证据时，公证成功也不等于 MVP 全项通过。
